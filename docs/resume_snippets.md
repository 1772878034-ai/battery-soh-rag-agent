## 项目条目（推荐写法）

**锂电池 SOH 预测与 RAG 智能问答 Agent** ｜ 个人项目 ｜ Python / LangChain / Transformers

- 设计 **BM25 + FAISS 混合检索、BGE CrossEncoder 重排**的 RAG 问答链路：双路召回经 RRF
  融合后做二次排序；自建 18 题标注评估集（含语义改写），**Hit@1 由 0.28 提升至 0.89、
  MRR 由 0.54 提升至 0.94**，并定位出“等权 RRF 被弱检索器拖累、BM25 缺中文分词”两个关键问题。
- 在 RAG 之上实现**最小 Agent**：LLM 按工具 schema 输出 JSON 任务计划（带规则路由兜底），
  注册知识库检索、LSTM SOH 预测、计算器三类工具，支持后一步以模板引用前一步结果；
  规划前按意图裁剪工具调用，避免小模型过度规划。
- 实现**会话窗口 + 事实槽记忆**（JSON 持久化），支持跨轮指代解析（如“再循环 50 次”
  自动解析为具体循环数）；回答采用“**数值结论确定性拼装 + 机理 prose 引用证据编号**”，
  并强制展示证据片段，把 0.5B 小模型的词语替换、公式编造类幻觉限制在可核验范围。
- 将 NASA B0005 容量衰减 LSTM（电流积分提容量、time_step=5）封装为 Agent 工具；
  完成 Streamlit 双标签页 Demo 与**全链路本地离线部署**，单轮问答约 34 s，支持一键复现。

## 面试可能追问与应答要点

1. **为什么加了重排提升这么大？** RRF 只按召回排名做倒数计分，无法判断 query 与 chunk
   的细粒度相关性；CrossEncoder 把 (query, chunk) 拼接过联合模型，输出语义相关性分数，
   直接纠正排序。代价是延迟从 ~15 ms 增至 ~189 ms。
2. **为什么混合 RRF 反而不如单路 FAISS？** 等权融合默认 BM25 与 FAISS 能力相当，
   但本项目 BM25 因未做中文分词近乎失效，它的错误排名通过 RRF 惩罚了正确 chunk。
   工程结论：融合权重应按检索器质量或查询类型动态分配，且必须有评估集验证，不能想当然。
3. **Agent 的规划怎么保证可靠？** LLM 规划 → JSON 解析与工具名/参数校验 → 意图裁剪
   → 执行期异常捕获；任一环节失败回退到确定性路由。数值结果不信任 LLM 复述，
   由工具输出确定性拼装。
4. **记忆具体做了什么？** 短期对话窗口 + 长期事实槽（last_cycle、battery_id），
   落盘 JSON；规划前做指代解析。未做摘要压缩/向量记忆，是已知的后续方向。
5. **LSTM 结果有什么水分？** 当前为全序列训练、同序列预测（in-sample），偏乐观；
   time_step=5 只能平滑追踪、不能外推。改进方案是按循环区间切分训练/验证并给置信区间。
